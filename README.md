# NoticeDiff

**Every Change. Clearly Communicated.**

NoticeDiff is a university lecture change and notification system. Instructors request changes to lectures,
an administrator approves or rejects them, and enrolled students are notified in the app only after approval.
The system records whether each request met the 24-hour notice rule and keeps a permanent history.

NoticeDiff records and measures notice. It cannot force instructors to use it or enforce a university policy.

## Technology

Linux (Ubuntu), Apache, MySQL, PHP (PDO), HTML, CSS and JavaScript. No frameworks.

## Roles

| Role | Can do |
|---|---|
| Student | Sign up, view own timetable (original and approved schedule), notifications, change history |
| Instructor | Submit change requests for own lectures, see request status and 24-hour deadlines |
| Administrator | Manage courses, sections, enrollments, the official timetable, approve or reject requests |

Public signup always creates a student. Instructor and administrator roles are assigned by an administrator in the database.

## Implemented features

- Registration and login with hashed passwords, PHP sessions, CSRF tokens
- Role-based access control, enforced on the server for every protected page
- Admin: user list, semesters, sections, courses, enrollments, official timetable
- Instructor request form: cancellation, reschedule, time change, room change, mode change
- Server-calculated 24-hour deadline, late flag, mandatory emergency explanation for late requests
- Admin approval and rejection with a confirmation dialog and recorded decision
- In-app notifications for enrolled students, with read and unread status
- Student weekly timetable showing original and approved schedules side by side
- Change history page with a request, approval and notification timeline
- Permanent audit table that the database refuses to edit or delete
- Admin audit report (late requests, decisions, notification counts) and a permanent history log
- Admin can create accounts with any role, change roles and disable or enable accounts
- Student commute preferences with schedule-impact warnings (a comparison of times the student enters, not a bus system)
- Instructor "My courses" page with students per section, upcoming lectures and pending requests
- Administrator transport check per request: how many enrolled students use the university bus and who would clash with a new time (advisory)

## Not implemented yet

Email notifications, a settings and profile page, a help page, a lecture details page,
reports and analytics charts, notification-log pages for administrators, 
calendar export, and the "additional lecture" change type in the request form.
Disabling an account takes effect at the user's next login.

## Running locally

1. Install Apache, MySQL and PHP with the `pdo_mysql` extension.
2. Point an Apache virtual host at the `public/` folder, for example `new.dev.local`, and add it to `/etc/hosts`.
   Only `public/` is served. `config/` and `includes/` stay outside the web root.
3. Create the database and tables:

```bash
sudo mysql -e "CREATE DATABASE noticediff CHARACTER SET utf8mb4;"
sudo mysql noticediff < database/schema.sql
```

4. Create a MySQL user limited to that database (`SELECT, INSERT, UPDATE, DELETE`).
5. Store the credentials in a private env file that is **not** committed to Git. The variables are
   `DB_HOST`, `DB_NAME`, `DB_USER` and `DB_PASS`. See `config/database.php` for the path it reads.
6. Register an account through the site, then promote it:

```bash
sudo mysql -e "UPDATE noticediff.users SET role='admin' WHERE email='you@example.com';"
```

Log out and in again so the session picks up the new role.

## Security notes

- Passwords are stored with `password_hash()` and checked with `password_verify()`.
- Every query uses prepared statements. Output is escaped with `htmlspecialchars()`.
- Session ID is regenerated at login. Cookies are `HttpOnly` and `SameSite=Lax`.
- State-changing forms carry a CSRF token that the server verifies.
- Times are stored in UTC and shown in Pakistan time. All timestamps are generated by the server.
- Triggers block UPDATE and DELETE on `change_history`.
- The login page gives one generic error so it does not reveal which emails exist.
